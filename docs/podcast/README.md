# idol批評podcast 構想

## 番組コンセプト

**データで見つけ、現場と文化で読み、次の問いを残す。**

この番組は、アイドルを単なるランキングや消費対象として扱わず、ライブ、楽曲、ファンとの関係、地域、制度、ビジネス、メディア表現を横断して批評する。`idol-p-agent` が収集・分析した事実を出発点にするが、データだけで人や文化を断定しない。数字に表れない経験、当事者の声、歴史的文脈、権力関係を必ず検討する。

## 初期フォーマット

| 項目 | 方針 |
|---|---|
| 長さ | 25〜40分。特集回は60分まで |
| 頻度 | 月2回を基本に、調査負荷を優先 |
| 形式 | ホストの批評、一次資料の紹介、反対仮説、次の問い |
| 対象 | アイドル文化、ライブ、楽曲、ファン、地域、制作、プラットフォーム |
| 成果物 | 音声、概要欄、引用・出典、文字起こし、次回調査メモ |
| トーン | 知的だが閉じない。断定よりも問いと検証可能性を重視 |

## 批評フレーム

各エピソードは、以下の順で構成する。

1. **問い** — 何を批評するのかを一文で定義する。
2. **観測** — `idol-db`、`idol-live`、`idol-research` などのデータから確認できる事実を示す。
3. **経験** — ライブ、楽曲、会話、ファン活動など、数字になりにくい具体的経験を扱う。
4. **構造** — 誰が利益を得るのか、誰の負担が見えなくなっているのか、どの制度・媒体が影響するのかを検討する。
5. **反対仮説** — 自分の見立てを崩す説明を最低1つ置く。
6. **提案** — 作品・運営・ファン・研究者・プロダクトの各立場から、実行可能な次の一手を示す。
7. **余韻** — 結論で閉じず、次に観測すべき問いを残す。

## エピソード候補

### 第0回：アイドルをデータベースにするとは何か

`idol-db` のcanonical layer構想を起点に、公開データの正規化が便利さと同時に何をこぼれ落とすのかを考える。データ契約、provenance、ライセンス、当事者性を番組の基本姿勢として宣言する。

### 第1回：無銭ライブは本当に無料なのか

`idol-live` が扱う無料、0円＋1D、予約必須などの差異を起点に、価格表示の裏にある移動費、時間、心理的コスト、運営負担を批評する。

### 第2回：「売れた」と「届いた」は同じか

`idol-produce` / `idol-produce-or` の visible value と invisible value、FAN TRUST の考え方を紹介し、再生数・売上・継続関係の違いを考える。

### 第3回：地域×年代でアイドルを見る

`idol-map` と `idol-lab` の接続から、地域文化を発見可能にすることの可能性と、地域・歴史・当事者を類型化する危うさを扱う。

## `idol-p-agent` からの生成物

各分析実行後、番組化できる論点を次の形式で抽出する。

```yaml
episode_pitch:
  title: ""
  central_question: ""
  evidence:
    - repository: "bonsai/idol-db"
      path_or_signal: ""
      observed_fact: ""
  lived_context: ""
  counter_hypothesis: ""
  guests_or_primary_sources: []
  proposed_action: ""
  sensitivity_notes: ""
  confidence: "low|medium|high"
  next_validation: ""
```

**観測事実と批評的解釈は分離**し、privateリポジトリの内容、未公開情報、個人情報、根拠のない人物評価はエピソード素材にしない。実在の個人・グループ・運営を扱う回では、一次資料の確認と反論機会を設ける。

## 収録前チェックリスト

- 中心問いが一文で言えるか
- 出典URLと取得日があるか
- データの限界・欠測・偏りを説明できるか
- 反対仮説を一つ以上検討したか
- 個人攻撃、未確認情報、private情報が入っていないか
- 批評対象と広告・協賛・取材関係を明示できるか
- 聴取後にリスナーが検証できる資料を用意したか

## 最初の運用

まずは第0回の台本をテキストで作成し、10〜15分の短い試作として収録する。反応を見る前に、音質や配信先の最適化よりも、出典提示・批評の公平性・継続可能な調査負荷を検証する。番組が継続できる見込みが立った段階で、文字起こし、RSS、配信先、音声生成・編集の自動化を追加する。
